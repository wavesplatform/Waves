# RIDE evaluator

## The evaluator rewrites the script tree in place

`EvaluatorV2` evaluates by writing results back into the tree: `FUNCTION_CALL.args`, `BLOCK.body`, `GETTER.expr`, `IF.cond` and `LET.value` are `var`s, and a reference to a `LET` replaces its value with the evaluated one, which is how LETs are lazy and evaluated once. So it must never run on the tree a script holds, which is shared between invocations and threads. `EvaluationCopy` makes the copy it runs on, and copies only what gets written into before the evaluator reaches it:

- Leaves (`REF`, evaluated constants, `FAILED_*`) are immutable and shared.
- Function declarations are shared: a user function call copies the function body (`evaluateUserFunction`) and evaluates the copy, never the body in place.
- A `LET` is a new node whose value is still the original's, marked with `LET.valueShared`. `evaluateRef` copies the value when it first evaluates it, so values nothing references are never copied. `valueShared` is a body field, not part of `LET`'s equality.
- An `IF` is a new node whose branches are still the original's, marked with `IF.branchesShared` when either branch is not a leaf. `evaluateBranch` copies only the branch it takes, so `match` arms that are not taken are never copied. Like `valueShared`, `branchesShared` is a body field outside equality.

Anything that starts evaluating a tree, or adds a path that writes into one, has to keep to this: a node written into must have been copied first. In particular, never rebuild a `LET` (`copy`, `LET(name, value)`) or an `IF` (`copy`, `IF(cond, ifTrue, ifFalse)`) between `EvaluationCopy` and its first evaluation: the new node drops `valueShared` or `branchesShared` while still holding the original value or branches, and the evaluator would write into the shared tree. `EvaluatorV2Test` evaluates one tree twice and checks it is unchanged afterwards.

`EXPR.deepCopy` (through `cats.Eval`) is no longer used by the evaluator and is kept on purpose: it is the reference `EvaluationCopyTest` compares against and the baseline in `FunctionCallCopyBenchmark`. It allocated several objects per node and copied whole dApps for every invocation.

## The evaluator runs on an explicit stack, not Monix

`EvaluatorV2` used to build every step as a `Coeval[Either[...]]`, later as steps of `EvaluationResult`, a small trampoline of its own; both allocated a closure for every continuation and for every place a value is written. Now `EvaluatorV2.run` is a single loop over a `java.util.ArrayDeque` of frames: a frame says what to do with the unused complexity when the subexpression above it finishes (`CallFrame` evaluates the next argument or calls the function, `GetterFrame`, `IfFrame`, `LetFrame`, `NewModeFrame`, `PrecalculatedFrame`), and a `Slot` says where the value of a subexpression is written (the old `update` callbacks). Each frame does exactly what the `flatMap` it replaced did, in the same order, so complexity, error texts and the log are unchanged; keep it that way, they end up in the state. An error skips every frame except `LetFrame`, which logs it (the old `logError`). The only exceptions caught are those of a native function call, turned into `An error during run ...` with complexity 0 as before; any other non-fatal exception leaves `run`, and `applyLimitedCoeval` still turns it into `Left((e.getMessage, limit, log))`. `BlockSlot` passes a value up through nested blocks in a `@tailrec` loop, so deep nesting does not grow the call stack. `Extended` native functions (`invoke` and friends) still return a `Coeval`; see the next paragraph for how it runs.

Measured on testnet 2368890 to 2398890 on Linux, the procedure under Measuring with two runs of each variant alternating: 479 s and 467 s on the trampoline, 394 s and 374 s on the explicit stack, 19% less import time, with RocksDB contents identical (entry count and SHA-256 per column family). The trampoline's own loop was a sixth of the appender in profiles; the closures every step allocated (one per `flatMap`, one per `update`) cost more than the loop itself showed.

An invoke between dApps evaluates the callee in a nested evaluation (`DAppEnvironment.callScript`, `InvokeScriptDiff`, `ContractEvaluator`, a new `EvaluatorV2.run`). None of that may run on the caller's call stack: a chain of up to 100 invokes would then need a stack 100 levels deep, a `StackOverflowError` is fatal and nothing catches it, and nodes with different stack sizes would disagree about a block. So `Run` does not run an `Extended` function: it stops with the function's `Coeval` (`SuspendedCall`), `EvaluatorV2.run` hands it to Monix with `flatMap`, and resumes the loop with the result. Everything between two evaluations composes as `Coeval` (`CoevalR` in `InvokeScriptDiff`), so the whole chain runs in Monix's stack-safe run loop; a `.value()` anywhere on that path brings the nesting back. #4144 introduced exactly that (its trampoline ran the `Coeval` eagerly inside a step, and the previous evaluator had composed it), and #4152 removed it. `SyncDAppLimits` runs the deepest allowed chain on a thread with a 256 KB stack, where nested runs overflow. Suspending at invokes cost nothing measurable: on the slice below, 365 s and 355 s against 468 s for base, with identical RocksDB contents.

Monix stack tracing (`monix.eval.stackTracingMode`, `cached` by default) cost 7% of the slice below while every evaluator step ran on `Coeval`. Once `Coeval` left the per-step path (measured on the trampoline, 2146124 to 2176100 on one machine: 269.6 s with it off, 269.5 s with it on) it made no difference, so the node keeps the Monix default.

## ScopeEvaluator: scopes instead of rewriting the tree

`ScopeEvaluator` evaluates against chains of scopes (`LetCell`, `FuncEntry`, innermost first, like EvaluatorV2's list of enclosing blocks) and never writes into the tree, so it copies nothing. `EvaluatorV2.applyLimitedCoeval` picks the evaluator from `ScopeEvaluator.mode`, set by `-Dwaves.evaluator=v2|scope|check` (default `v2`). It reproduces EvaluatorV2's result, unused complexity and log for every evaluation that completes or fails, including its quirks: the old-mode overhead of 1 per REF, GETTER and IF branch, with a REF to a LET (but not a global) needing complexity left; newMode's 1 for a call that spent nothing and the precalculated limit of context functions; dynamic scope when `correctFunctionCallScope` is off; arguments bound with `zip`, the later shadowing the earlier.

It does not reproduce EvaluatorV2's partial trees. Where EvaluatorV2 would stop with an incomplete result (complexity left is not enough for the next step), it gives up and the evaluation is run again on EvaluatorV2. A plain rerun would read the state the first run's invokes changed, so every evaluation records its environment calls (`RecordingEnvironment`, the results of `callScript` included) and the rerun replays them (`ReplayingEnvironment`), then goes on live from where the first run stopped, which is where EvaluatorV2 would have been. A partial tree only ever mattered for continuations; now only `IncompleteResult`'s unused complexity is used, and it reaches the state through failed invokes.

The log dedupes entries by LET node identity (`EnabledLogEvaluationContext.loggedLets`). EvaluatorV2 had one node per LET outside function bodies, the one `logCall` logs the invocation argument with, and a fresh node per call inside them, so a cell is keyed by its original node when the LET is outside every FUNC body of the script, and by a node of its own otherwise. EvaluatorV2 logs a LET when the value is written into it, before the `NewModeFrame` and `PrecalculatedFrame` of the call that produced it run, so `logLetAhead` logs it at that point too. A context function such as `value()` gets its arguments as EvaluatorV2 had rewritten them: every call among them with its arguments evaluated (`CallFrame.startArgs`), which `value()` builds its error message from.

Check mode runs every evaluation on ScopeEvaluator and then on EvaluatorV2 with the recorded environment (strict: a call beyond the record throws instead of reaching the state), and reports any difference in result, complexity or log through `ScopeEvaluator.onMismatch`. The importer halts on the first one. Tests that count native calls through a side effect (`EvaluatorV1V2Test` "let is evaluated maximum once", "each argument is evaluated maximum once for user function") fail in check mode by design. `ScopeEvaluatorTest` compares the raw evaluators at every limit from 0 to the full cost, in both modes and both function call scopes, which is where the two differ most.

## `wavesBalance` computes the generating balance lazily

The generating balance walks up to 1000 blocks of balance history (`RocksDBWriter.balanceSnapshots`), so `BalanceDetails.generating` is a lazy field and the `BalanceDetails` object holds its fields in `Terms.LazyLongFields`; the weight is the same as before, since every field is a `CONST_LONG`. The generating balance is computed against the blockchain current at the call, because a nested invoke replaces `currentBlockchain()` before the script reads the field. On testnet it barely helps: dApp scripts read `.generating` in about 83% of `wavesBalance` calls, so it removed 17% of the history walks on the slice and nothing measurable from a full import (3h10m32s before, 3h11m23s after).

## Script estimation

A `SetScript` transaction estimates every callable of the dApp against the whole dApp, once for the current estimator and once for every later one (`SetScriptTransactionDiff.estimate`), then the verifier (`DiffsCommon.countVerifierComplexity`). The estimators run on `TaskMT`, a state monad over `cats.Eval`, so this costs like the evaluator did before the changes above. Past testnet height 2.1M scripts are set over and over: from 2146124 to 2408350, 10,763 `SetScript` transactions set 3,587 distinct scripts, the most common one 270 times. `SetScriptTransactionDiff` keeps the complexities of the last 1,000, keyed by a hash of the script bytes and `EstimationSettings`, every blockchain setting the estimation reads (estimator, RideV6, reduced verifier limit, estimation overflow check, V1 pre-check). The estimation takes `EstimationSettings` instead of a `Blockchain`, so a new setting it needs has to go into that class and with it into the key; reading the blockchain directly again would let a script set under the new setting get the old complexities. `SetScriptEstimationCacheTest` sets one script under settings that estimate differently. Moving the estimators off `cats.Eval` would be a larger, consensus-relevant change, since stored complexities depend on them.

## Measuring

Import a dApp-heavy stretch of testnet: import once to 2146124 (`waves import -i <blocks-file> -h 2146124`), keep a copy of that `data` directory, and time each variant importing from a fresh copy of it with `-h 2176100`. Over those 30k blocks 94% of block appending is `InvokeScriptTransactionDiff`; any stretch past 2.1M works the same way. To check that a change leaves consensus alone, compare the resulting databases of both variants: open each read-only with RocksDB and hash every key and value per column family (entry count and SHA-256); they must be identical. With the JProfiler agent started from a config file, take intermediate snapshots with `jpcontroller -n <pid>` (`saveSnapshot <path>`); attaching another session replaces the agent's settings.

On that slice the changes above took the import from 695 s to 300 s on Linux; the same code takes about 270 s on an Apple silicon Mac, which is the baseline for further work on that machine. Profiles from before the explicit stack showed the trampoline's own loop at about a sixth of the appender, then name lookups (`visitRef`, now `findLet`, and `findUserFunction`), copying function bodies at every call, and signature checks scripts make (`sigVerify`); the lookups and copies are still there.

Tried and dropped in the trampoline loop, before it was replaced: keeping the current value and an error flag in two variables instead of a `Right` per `map` step, applying `map`/`flatMap` directly when the source is already a value (`Now`) instead of pushing and popping it, and ordering the loop's match by frequency. On a mainnet import past height 4.6M `EvaluationResult.run` stayed at 6% of the appender and script complexity per second did not change, so its share is most likely evaluator code inlined into it, not the loop. PR #3792 (a draft) rewrote the evaluator with scopes instead of tree rewriting and with invokes inside the same loop, but it also changed complexity counting and function scope; any of its ideas has to come in on its own and leave results unchanged.

Profiles from JProfiler's async sampling on macOS are not reliable for proportions: they put 40 to 50% of the appender into the `write` syscall under RocksDB's WAL, where RocksDB's own timers measure 2 to 8%. Use Linux for profiles, and RocksDB statistics for the database share. Two indexes for name lookups were tried and measured no faster: a persistent `HashMap` updated on every block the evaluator enters, and an index of the top-level declarations built once per evaluation (267 s against 270 s on the slice). The `visitRef` share in profiles most likely includes the evaluation inlined into it, not just the walk over the enclosing blocks.

What did pay off is skipping the walk for names no LET in scope declares. Counted over 10k blocks past testnet 3.108M, `findLet` found the LET in 226M lookups (8 blocks walked on average) and missed in 62M (62 blocks on average, 3.85G of the 5.6G blocks walked), almost all of them globals (`nil`, `unit`, `this`, `height`). `Run` keeps `enteredLets`, the names of every LET it has entered, and a `REF` whose name is not in it goes straight to `evaluateGlobalVar`. This is correct only while every scope list a `Run` uses is built from blocks it entered itself: `Run` starts with no blocks, and the `BLOCK_DEF` case of `evaluate` is the only place that pushes one and records its name. Seeding a `Run` with an outer scope, or pushing a block anywhere else, would resolve a LET that shadows a global (scripts on testnet shadow `lastBlock`, `height` and `this`) to the global and change state. `EvaluatorV2Test` covers a LET and a function argument shadowing `height`. On testnet 3108228 to 3138228 it took 482.7 s (five runs) down to 460.5 s (three runs), with RocksDB contents identical. Copying only the taken `IF` branch showed no measurable difference on the same slice (464.0 s with it, 460.4 s and 459.0 s without); it is kept because it never copies more than before.
